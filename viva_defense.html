Chapter 13 Autonomous Agents & Search

1. NP-Hardness of Index Selection (ISP)

Formulated as subset selection over candidate pool $\mathcal{C}$ under budget $B$: $$\mathcal{I}^* = \arg\max_{\mathcal{I} \subseteq \mathcal{C}, \text{Size}(\mathcal{I}) \le B} \sum_{i=1}^m w_i \Delta \text{Cost}(Q_i \mid \mathcal{I})$$ Proven NP-hard via polynomial reduction from 0-1 Knapsack.

2. The Non-Additive / Submodular Trap

Classical 0-1 Knapsack assumes additive item values $V(S) = \sum v_i$. In databases, index benefits are submodular:

  • Composite indexes subsume single indexes ($I_{(A, B)}$ zeros the marginal value of $I_{(A)}$).
  • Indexes flip CBO join paths from Hash Join to Index Nested Loops, dynamically altering access paths.
Dynamic Programming $\mathcal{O}(n \cdot B)$ completely fails.

3. The Winning Hybrid 3-Stage Agent

Resolves the duality between Pure LLM (hallucinates byte arithmetic, fails at $2^{|\mathcal{C}|}$) and Pure MCTS ($>3,500$ blind action explosion):

  1. Stage 1 (AST Miner): Prunes space to $30 \le |\mathcal{C}| \le 50$ high-value candidates.
  2. Stage 2 (MCTS Solver): Explores $2^{|\mathcal{C}|}$ under budget $B$ over a zero-byte cost engine ($< 0.4\text{ ms}$).
  3. Stage 3 (Live ReAct Verifier): Materializes indexes physically and heals regressions via a Tabu list.

4. UCT Tree Policy via Hoeffding Bound

Balances exploitation and exploration: $$\text{UCT}(s, a) = Q(s, a) + c \cdot \sqrt{\frac{\ln N(s)}{N(s, a)}}$$ Setting tail risk $\delta = N(s)^{-4}$ in Hoeffding's inequality yields the theoretical constant $c = \sqrt{2} \approx 1.414$.

5. Mackert-Lohman Selectivity Crossover

Unclustered B-Tree scans perform random heap dereferences ($c_{\text{random}} = 1.5$): $$\sigma^* \approx \frac{1}{\text{TuplesPerPage}} \cdot \frac{c_{\text{page}}}{c_{\text{random}}} \approx 1.3\% - 15\%$$ When $\sigma > \sigma^*$ (e.g. TPC-H Q1 where $\sigma=0.98$), unclustered indexes thrash the buffer cache, causing a **40% slowdown**.

6. Leftmost Prefix Invariant

Relational algebra dictates that composite indexes must be ordered **Equality-First**: $$(C_{\text{equality}}, \; C_{\text{range}})$$ Equality isolates an exact sub-tree leaf partition, enabling contiguous binary search on range columns. Range-first destroys seek pruning.

Computational Complexity & Submodular Knapsack Limits
Why does classical 0-1 Knapsack Dynamic Programming ($\mathcal{O}(n \cdot B)$) completely break down when applied to general physical database index selection?
A
Knapsack requires independent, additive values $V(S) = \sum v_i$; index benefits are submodular and non-additive because existing indexes cause plan subsumption, join method flips, and interaction effects across queries.
B
B-Tree storage footprints on disk cannot be estimated deterministically due to unpredictable page fill-factor variations and text compression.
C
The storage budget constraint $B$ operates in continuous floating-point memory space rather than discrete integer capacities.
D
Relational cost-based optimizers strictly restrict each query execution plan to at most one index per database.
Examiner Solution & First-Principles Defense Verified
1. Reduction from 0-1 Knapsack: In our formal thesis, we prove that the Index Selection Problem (ISP) is NP-hard by polynomial-time reduction from 0-1 Knapsack (constructing independent single-table queries where each index has fixed size $w_i$ and fixed benefit $v_i$).
Why Knapsack Dynamic Programming Fails in Real Databases
The Bellman dynamic programming equation for Knapsack: $$V(i, w) = \max\Big(V(i-1, w), \; V(i-1, w - w_i) + v_i\Big)$$ fundamentally assumes that the value of item $i$ ($v_i$) is constant, independent, and strictly additive regardless of which other items coexist in the knapsack.

In real database workloads, index benefits are non-additive and submodular:
  • Index Subsumption: If composite index $I_{(A, B)}$ is materialized, the marginal cost reduction of single-column index $I_{(A)}$ drops to zero.
  • Join Path Shifts: Adding an index on Table 1 can cause the CBO to switch from a Hash Join to an Index Nested Loops Join, completely altering the utility and access paths of indexes on Table 2!
Because subproblem optimality depends on the specific combination of coexisting indexes, subproblems cannot be memoized by remaining capacity alone without storing the entire exponential state $2^{\mathcal{C}}$.
Question 2
MCTS State-Space Pruning & Canonical Ordering
In `src/mcts/mcts_solver.py`, why does child node expansion enforce canonical subset ordering via `self.candidate_pool[action_idx + 1 :]` rather than allowing any unselected candidate?
A
It eliminates $k!$ permutation symmetries for identical index subsets, preventing the search tree from duplicating identical configurations and diluting UCT visit counts across redundant branches.
B
It forces index creation DDL statements to execute in strict alphabetical schema order to prevent database catalog transaction deadlocks.
C
It ensures that candidate index storage sizes strictly decrease down any tree branch, satisfying the monotonicity invariant.
D
It isolates candidate indexes across different tables to prevent race conditions during concurrent multi-threaded cost evaluations.
Examiner Solution & First-Principles Defense Verified
Whiteboard Derivation: The $k!$ Permutation Pathology
A physical database index configuration is an unordered set: $$\{I_A, I_B, I_C\} \equiv \{I_C, I_A, I_B\}$$ If an MCTS implementation naively allows any unselected candidate (cand not in state) to be added at each tree expansion step:
  • A configuration of $k$ indexes can be reached through $k!$ distinct paths in the search tree.
  • For a 4-index design, there are $4! = 24$ identical leaf states scattered across different subtrees.
  • Each duplicate leaf maintains separate visit counts $N(s)$ and sample reward means $Q(s, a)$.
The UCT tree policy: $$\text{UCT}(s, a) = Q(s, a) + c \cdot \sqrt{\frac{\ln N(s)}{N(s, a)}}$$ relies on concentrated visit counts $N(s, a)$ to exploit the most promising paths. When statistics are fragmented across $k!$ duplicate branches, visit counts are heavily diluted, and the MCTS solver wastes its 500 rollout iterations repeatedly re-simulating the same physical subset.

The Canonical Ordering Fix: Enforcing self.candidate_pool[action_idx + 1 :] guarantees that every subset $\{I_1, I_2, \dots, I_k\}$ has exactly one unique canonical path in the tree. This collapses the search space from permutations $\sum_{k} \frac{N!}{(N-k)!}$ down to combinations $\sum_{k} \binom{N}{k} = 2^N$.

MCTS Foundations: Hoeffding's Inequality & $c = \sqrt{2}$
Provide the mathematical derivation showing why the optimal exploration constant in the UCT tree policy is $c = \sqrt{2} \approx 1.414$.
A
Applying Hoeffding's Inequality $\mathbb{P}(\mu > \bar{X} + \epsilon) \le \exp(-2n\epsilon^2)$ with polynomial tail probability decay $\delta = N(s)^{-4}$ yields $-2n\epsilon^2 = -4\ln N(s) \implies \epsilon = \sqrt{2}\sqrt{\frac{\ln N(s)}{n}}$.
B
$\sqrt{2}$ represents the diagonal length of a unit square in SQLite's 2D R-Tree spatial indexing engine.
C
It is derived from the Nyquist-Shannon sampling frequency limit across continuous SQL query workloads.
D
The value is empirically chosen by grid search because SQLite locks tables after exactly 1.414 seconds.
Examiner Solution & First-Principles Defense Verified
Whiteboard Proof: Derivation of UCT Constant $c = \sqrt{2}$
Let $X_1, \dots, X_n \in [0, 1]$ be independent reward samples from candidate index action $a$ with true mean $\mu_a$ and empirical sample mean $\bar{X}_{a, n} = \frac{1}{n}\sum_{i=1}^n X_i$.

1. Hoeffding's Inequality (Auer et al., 2002): $$\mathbb{P}\left(\mu_a > \bar{X}_{a, n} + \epsilon\right) \le \exp\left(-2 n \epsilon^2\right)$$ 2. Bounding Exploration over Parent Visits $N(s)$: To ensure that sub-optimal actions are explored with vanishingly small probability as the total parent visits $N(s)$ grow, set the error probability tail to $\delta = N(s)^{-4}$: $$\exp\left(-2 n \epsilon^2\right) = N(s)^{-4}$$ 3. Solving for the Confidence Radius $\epsilon$: $$-2 n \epsilon^2 = -4 \ln N(s) \implies \epsilon^2 = \frac{4 \ln N(s)}{2 n} = \frac{2 \ln N(s)}{n}$$ $$\epsilon = \sqrt{2} \cdot \sqrt{\frac{\ln N(s)}{n}}$$ Therefore, with high probability ($1 - N(s)^{-4}$): $$\mu_a \le \bar{X}_{a, n} + \sqrt{2} \cdot \sqrt{\frac{\ln N(s)}{N(s, a)}} \quad \blacksquare$$
Question 4
Physical Cost Modeling & Selectivity Crossover ($\sigma^*$)
Why did materializing an index on `l_shipdate` for TPC-H Q1 cause a 40% performance regression in SQLite, and how does the Mackert-Lohman cost model derive the crossover threshold $\sigma^*$?
A
High predicate match ($\sigma = 0.98$) causes unclustered index scans to dereference table heap rows via non-sequential pointers, reading identical pages repeatedly across random disk seeks ($c_{\text{random\_io}}=1.5$); sequential scans read contiguous pages once with kernel prefetching ($c_{\text{page\_io}}=1.0$).
B
SQLite disables database buffer caching whenever an unclustered index matches more than 20% of rows, forcing raw disk reads on every operator.
C
Unclustered B-Tree index leaf nodes must be dynamically locked and rebalanced by the database engine during SELECT query plan execution.
D
Sequential scans completely bypass CPU tuple evaluation cost ($c_{\text{cpu\_tuple}} = 0$) by pushing down filter predicates into disk controller SIMD instructions.
Examiner Solution & First-Principles Defense Verified
Whiteboard Derivation: Mackert-Lohman Selectivity Crossover ($\sigma^*$)
In physical database design, an index scan is not always faster than a sequential table scan:

1. Sequential Table Scan Cost: $$\text{Cost}_{\text{seq}} = N_{\text{pages}} \cdot c_{\text{page\_io}} + N_{\text{rows}} \cdot c_{\text{cpu\_tuple}}$$ 2. Unclustered Index Scan Cost: $$\text{Cost}_{\text{index}}(\sigma) = \left(h_{\text{tree}} + \sigma N_{\text{leaf\_pages}}\right) c_{\text{page\_io}} + \min(N_{\text{pages}}, \sigma N_{\text{rows}}) c_{\text{random\_io}} + \sigma N_{\text{rows}} c_{\text{cpu\_tuple}}$$ Where $c_{\text{page\_io}} = 1.0$ (sequential block read) and $c_{\text{random\_io}} = 1.5$ (unclustered random page seek).

3. Equating Costs at Crossover $\sigma^*$: For non-covering indexes where random heap lookups dominate: $$\sigma^* \cdot N_{\text{rows}} \cdot c_{\text{random\_io}} \approx N_{\text{pages}} \cdot c_{\text{page\_io}}$$ $$\sigma^* \approx \frac{N_{\text{pages}}}{N_{\text{rows}}} \cdot \frac{c_{\text{page\_io}}}{c_{\text{random\_io}}} = \frac{1}{\text{TuplesPerPage}} \cdot \frac{1}{1.5} \approx \mathbf{1.3\% - 15\%}$$ The Q1 Regression: The predicate WHERE l_shipdate <= '1998-09-02' matches 98% of the relation ($\sigma = 0.98 \gg \sigma^*$). Materializing an index on l_shipdate caused SQLite's naive CBO to execute 22,000 random heap page dereferences, degrading latency from $27\text{ ms}$ to $38\text{ ms}$ (a 40% slowdown).

Question 6
Relational Schema Invariants & Primary Key Pruning
Why are single-column primary keys (e.g. `o_orderkey`, `c_custkey`) stripped from candidate pool $\mathcal{C}$ in `candidate_miner.py`, while composite keys containing primary keys are preserved?
A
Database engines automatically maintain unique B-Trees for primary keys upon creation; adding secondary single-column PK indexes is 100% redundant and burns budget B, while composite indexes enable covering scans.
B
SQLite's DDL compiler raises a fatal syntax exception if a developer creates an index containing any column declared as PRIMARY KEY.
C
Primary key columns have near-zero selectivity ($\sigma = 0$), which causes a divide-by-zero floating-point exception in the Mackert-Lohman index cost formula.
D
Hypothetical primary key indexes cannot be evaluated in memory because primary keys require persistent disk transaction journaling in SQLite's dbstat catalog.
Examiner Solution & First-Principles Defense Verified
Relational Catalog Invariants: When a table is created with a PRIMARY KEY, relational databases (including SQLite, PostgreSQL, MySQL) automatically build an internal unique B-Tree index (e.g. sqlite_autoindex_orders_1). In SQLite, an INTEGER PRIMARY KEY is an alias for the rowid itself, forming the clustered index of the table.
Why Single PK is Pruned but Composite PK is Preserved
  • Single-Column Secondary PK Index: Creating CREATE INDEX idx_o_orderkey ON orders(o_orderkey) builds a 100% redundant secondary structure. It duplicates existing pointers, burns physical storage budget $B$, and adds write-amplification overhead during DML operations without offering any novel access path.
  • Composite Secondary Index Containing PK: Creating CREATE INDEX idx_orders_cust_order ON orders(o_custkey, o_orderkey) is highly valuable. It provides an efficient index on foreign key o_custkey, while appending o_orderkey enables Index-Only Covering Scans for join queries, allowing the engine to satisfy queries directly from the B-Tree leaf pages without performing random heap lookups.
Question 7
Relational Algebra: Leftmost Prefix & Composite Key Ordering
In `_order_columns_equality_first()`, why must equality and equi-join columns strictly precede range columns in a composite B-Tree index?
A
An equality predicate isolates an exact contiguous partition in B-Tree leaves, allowing subsequent range columns to be point-seeked; placing range first fans out across multiple leaf pages, destroying seek pruning for subsequent columns.
B
Composite indexes with range columns leading cause immediate disk corruption in SQLite's B-Tree cell format.
C
SQL standards mandate that all equality columns be evaluated before range operators in the AST.
D
Placing range first causes the MCTS reward function to evaluate to negative infinity.
Examiner Solution & First-Principles Defense Verified
B-Tree Multi-Column Seek Pruning Mechanics
In a composite B-Tree with keys $(C_1, C_2)$ ordered lexicographically:

Case 1: Equality-First $(C_{\text{eq}}, C_{\text{range}})$: The query predicate $C_{\text{eq}} = v$ acts as an exact coordinate seek down the B-Tree directory nodes, landing directly on a single contiguous partition in the leaf pages. Within that leaf partition, $C_{\text{range}}$ is already sorted, so the storage engine can execute a binary search to find the lower bound and perform a contiguous range scan. Both columns actively prune index blocks.

Case 2: Range-First $(C_{\text{range}}, C_{\text{eq}})$: The inequality comparison $C_{\text{range}} \ge v$ spans across potentially hundreds of leaf pages. Because $C_{\text{eq}}$ is only sorted locally within each distinct value of $C_{\text{range}}$, the B-Tree cannot do a point seek on $C_{\text{eq}}$. The engine is forced to scan every leaf tuple across that entire range span to filter $C_{\text{eq}}$ sequentially!

Question 10
Search Convergence: Branching Factor Capping
In `src/mcts/mcts_solver.py` (line 145), child untried actions are capped to the top 8 candidates (`[:8]`). What algorithmic trade-off does this cap enforce?
A
It bounds tree width, allowing MCTS to traverse deeper multi-index combinations and concentrate rollout evaluations within a bounded budget of 500 iterations instead of shallowly fanning out across 40 wide branches.
B
Python's recursion limit throws a `RecursionError` if a node has more than 8 child pointers.
C
It limits the maximum number of indexes on the physical database to exactly 8.
D
It is required by the UCT policy to ensure the exploration constant $c$ remains real-valued.
Examiner Solution & First-Principles Defense Verified
The Search Width vs. Search Depth Trade-Off: With a candidate pool of $|\mathcal{C}| = 40$: If a node expands with an unconstrained branching factor of 40: - In 500 iterations, the root node would spend 40 iterations just visiting its immediate single-index children once! - The tree would remain extremely shallow (depth 1 or 2), never discovering synergistic 3-way or 4-way index combinations across tables.

Why Cap at 8? Because candidates in `self.candidate_pool` are already pre-ranked by relevance score from Stage 1's AST miner: - Restricting branching factor to the top 8 relevant candidates keeps tree branching narrow ($b \le 8$). - In 500 iterations, MCTS can explore deep paths (depth 4 to 6), evaluating complex multi-table configurations like $\{I_{\text{orders}}, I_{\text{customer}}, I_{\text{lineitem}}\}$ while retaining high statistical confidence in UCT selection.
